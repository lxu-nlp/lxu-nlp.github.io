0全景鸟瞰：一条消息的一生

先建立整体图景。nanobot 的核心是一个异步消息驱动的 agent：Channel（Telegram / Discord / WebSocket…）把外部消息发布到 MessageBus，AgentLoop 从总线消费消息并为每条消息创建独立 task，每个 task 内部走一条固定的Turn 流水线，流水线的核心阶段把实际对话交给 AgentRunner —— 一个「调 LLM → 执行工具 → 再调 LLM」的迭代循环。

贯穿全文的例子（先记住这个场景）

用户阿川在 Telegram 里对 bot 说：「看看 /workspace/todo.txt 里有什么，再告诉我一共有几行」。他的会话 key 是 telegram:8848，此前已经和 bot 聊过 10 条历史（这一点在讲 compaction 时会再次用到）。接下来每一节都用同一个例子往下推：run() 怎么接住这条消息（§1）→ restore/build 怎么准备会话和上下文（§4）→ 工具怎么循环（§6）→ 上下文超预算了怎么压缩（§8）→ 最终回复怎么发回 Telegram（§4 save/respond）。

一图记忆法

run() 负责「接」（从总线拿消息、分流、建 task），_process_message() 负责「排」（七个固定阶段的状态机），_run_core() 负责「转」（LLM 与工具之间的迭代循环）。三层各自独立演化，通过 TurnContext / AgentRunResult 两个数据结构衔接。

1AgentLoop.run()：主循环与消息分流

run() 是整个 agent 的入口，本质是一个带 1 秒超时的消息泵。每条消息处理成独立 task是刻意设计：主循环永远不被长任务阻塞，/stop 命令因此始终能得到响应。

nanobot/agent/loop.py : 1261-1377真实源码（节选）
async def run(self) -> None:
    """Run the agent loop, dispatching messages as tasks to stay responsive to /stop."""
    self._running = True
    try:
        logger.info("Agent loop started")
        while self._running:
            try:
                msg = await asyncio.wait_for(self.bus.consume_inbound(), timeout=1.0)
            except asyncio.TimeoutError:
                self._check_expired_sessions_if_due()   # 空闲期顺带做过期会话清理
                continue
            ...
            raw = msg.content.strip()
            effective_key = self._effective_session_key(msg)   # 归一化会话 key

            if await agent_context.handle_runtime_control(self, msg, self.tools):
                continue                                    # ① 运行时控制指令，不进 LLM
            if msg.require_existing_session and self.sessions.get_cached(effective_key) is None:
                continue                                    # ② 要求已存在会话但会话不在 → 丢弃
            if msg.is_user_input:
                await self.runtime_event_publisher.user_input_accepted(msg, effective_key)
            if msg.channel != "system" and self.commands.is_priority(raw):
                await self._dispatch_command_inline(...)   # ③ 优先级命令（如 /stop）内联执行
                continue
            ...
            # ④ cron / local trigger 等自动化 turn：会话忙则推迟（deferred）
            for label, coordinator in self._automation_turn_coordinators:
                if coordinator.defer_if_active(msg, ...):
                    deferred = True; break
            if deferred:
                continue
            ...
            # （省略：pending queue 注入路由 —— 本篇不展开）
            task = asyncio.create_task(self._dispatch(msg))  # ⑤ 每条消息一个独立 task
            self._track_active_task(effective_key, task)
    finally:
        await self.aclose()

整理成更 readable 的伪代码：

run() 分流逻辑伪代码
LOOP FOREVER:
    msg = bus.consume_inbound()          # 最多等 1s；超时就检查过期会话再回来
    key  = effective_session_key(msg)     # channel:chat_id，可被统一会话覆盖

    IF 消息是运行时控制指令（切模型等）:  HANDLE_INLINE; CONTINUE
    IF 消息要求已有会话但不存在:        DROP;           CONTINUE
    IF 是优先级命令（/stop 等）:          内联执行命令;    CONTINUE
    IF 是自动化 turn 且会话忙:           推迟（deferred）; CONTINUE

    SPAWN TASK _dispatch(msg)             # 每条消息一个 task → 并发处理不同会话
    REGISTER active_task[key]             # /stop 可凭 key 精确取消
为什么 timeout=1.0？

不是为了限流，而是给主循环一个周期性回控制权的机会：空闲时执行 _check_expired_sessions_if_due()（TTL 过期会话归档），同时保证 /stop 之类管理命令的最坏等待不超过 1 秒。

分流优先级（记忆顺序）

运行时控制 > 会话存在性检查 > 优先级命令 > 自动化 turn 延迟 >（pending queue 注入，本篇略）> create_task(_dispatch)。核心思想：凡是能不进 LLM 就不进 LLM，把宝贵的 Turn 流水线留给真正需要模型的请求。

例子 · run()

阿川的消息从 Telegram channel 发布进总线；run() 消费后 effective_key = "telegram:8848"；内容不是命令、不要求已有会话、也没有自动化触发 → 一路落到最后一步 create_task(_dispatch(msg))。此时模型还没被调用过 —— 一切 LLM 相关的事都发生在 Turn 流水线里。

2_dispatch()：从 task 到 Turn

run() 创建的每个 task 都执行 _dispatch(msg)，它是一个薄壳：把消息交给 Turn 流水线，拿到响应后回发。真正干活的是它调用的 _process_message()。

nanobot/agent/loop.py : 1391-1441真实源码（骨架）
async def _dispatch(self, msg: InboundMessage) -> None:
    session_key = self._effective_session_key(msg)
    ...
    delivery = self.turn_delivery_factory.create(msg, session_key, enable_stream=True)
    response = await self._process_message(msg, pending_queue=pending, delivery=delivery)
    await delivery.complete(response, ...)        # ← 响应发回 channel

两点了解即可：同一会话的并发由 _get_session_lock 保证串行（不同会话天然并行）；响应回传统一走 TurnDelivery 抽象（turn_delivery.py），封装 started / running / complete / 流式转发，不同 channel 的投递差异都被它吸收。本篇不再展开并发与取消细节。

例子 · _dispatch()

阿川的 task 拿着 session_key = "telegram:8848" 进入这里：turn_delivery_factory.create(...) 创建绑定 Telegram 回信通道的 delivery → 调 _process_message(msg, ...) 开始 Turn 流水线。拿到响应后 delivery.complete(response) 才会真正把回复发到 Telegram（见 §4 save/respond）。

3TurnContext：一个 Turn 的状态载体

在进入流水线之前，_process_message 先构造 TurnContext（loop.py:133）—— 后续所有阶段都围绕它读写。理解它就理解了 Turn 的全部状态：

nanobot/agent/loop.py : 133-190字段分组解读（节选）
@dataclass
class TurnContext:
    msg: InboundMessage               # 原始入站消息（restore 阶段可能被替换：附件引用改写）
    session: Session | None           # 会话（restore 阶段 get_or_create）
    session_key: str                  # 归一化后的会话 key
    turn_id: str                      # "{session_key}:{time_ns()}"
    runtime: LLMRuntime | None        # 模型运行时（build 阶段解析：provider+model+参数）
    kind: TurnKind                    # USER | SYSTEM（SYSTEM = cron/子代理等内部触发）
    delivery: TurnDelivery            # 响应回传通道
    original_user_text: str | None   # 原始用户文本
    history: list[dict] | None        # session 历史（build 阶段取出）
    transcript_input / provider_state # 发给 runner 的两种对话形态（见 build 阶段）
    final_content: str | None         # 最终回复（run 阶段落定）
    stop_reason / failure_error_kind  # "completed" / "error" / "max_iterations" ...
    usage / streamed_content / suppress_response
    events: EventSink                 # 流式事件管道（StreamDeltaEvent / StreamEndEvent...）
    ephemeral: bool                   # 不持久化的临时 turn（如摘要生成）
    hooks / hook_factories / turn_scopes
TurnKind.USER vs TurnKind.SYSTEM

用户消息是 USER；cron 触发、子代理（subagent）结果回注、Dream 记忆整理等内部消息是 SYSTEM。二者走同一条流水线，但细节不同：SYSTEM 不更新 original_user_text、不写 runtime context blocks、响应走 background_response 而非普通 outbound。

async def run(self, spec: AgentRunSpec) -> AgentRunResult:
    hook = spec.hook or AgentHook()
    messages, compaction = self._initial_transcript_and_compaction(spec)  # ← 见下
    context = AgentRunHookContext(messages=deepcopy(messages))
    llm_usage_source_token = bind_llm_usage_source(...)                  # usage 统计归因
    try:
        await hook.before_run(context)
        result = await self._run_core(spec, hook, messages, compaction)  # ← 真正的循环
    except asyncio.CancelledError:
        ...; raise                                          # stop_reason = "cancelled"
    except Exception as exc:
        ...; await hook.on_error(context); raise
    else:
        ...; await hook.after_run(context); return result
    finally:

        reset_llm_usage_source(llm_usage_source_token)

AgentRunSpec 是什么

关键点 1

对话历史是"滚雪球"的

每轮迭代只 append、不删改。无状态 provider 每次请求都重发整个列表 —— 这就是为什么需要上下文治理（§8）。有状态 provider 则只在服务端 append 增量（provider_state 路径）。

关键点 2

tool_call_id 是缝合线

assistant 的每个 tool_call 和后续 tool 消息靠 tool_call_id 一一配对。孤儿 tool result（配对的 tool_call 丢了）会被 drop_orphan_tool_results 清掉 —— 这是很多 provider 直接 400 的坑。

关键点 3

并行工具调用

模型可以在一条 assistant 消息里返回多个 tool_calls（比如同时读三个文件）。execute_tool_calls 按 concurrent_tools 并发执行，结果到齐后统一 append，再进入下一轮。

关键点 4

结果对模型是下一轮才可见

工具结果 append 完 → continue → 下一轮迭代重新请求模型。工具执行期间模型不"在线"；如果执行中用户插了新消息（injection），也会在下一次请求前被注入 messages 一起被模型看到。

关键点 5

超长结果的形态

如果 read_file 读回 500KB，normalize_tool_result 会把它写进工作区文件，tool 消息里只剩 "content": "结果过长，已保存至 .nanobot/tool-results/call_a1.txt" —— 模型需要时可以再调 read_file 分段读。

关键点 6

模型自己决定循环次数

runner 不编排"先读后数"—— 是模型看完工具定义和上下文后自己选择的。max_iterations 只防失控（比如模型陷入反复读同一个文件的循环），兜底时还会发一次无工具的收尾请求逼出总结。

请求层：_request_model 与流式处理runner.py:865

每次迭代的 LLM 请求入口。第一步永远是把 messages 交给 context_governor.prepare_request()（见 §8），拿到治理后的请求消息和 provider 上下文，然后构造请求参数并处理流式：每个 delta 通过 hook 转发（on_stream），原生 thinking 块有独立的开启/关闭事件对，流中断可恢复（_stream_recover）。工具调用结果里畸形调用（_drop_malformed_tool_calls）和收尾重试（_request_finalization_retry）也都在这一层的保护范围内。

为什么不直接调 provider？

_request_model 之前隔着 prepare_request（治理/压缩/预算校验），之后隔着流式事件归一化（stream/thinking/tool 事件）、usage 记录（_record_request_usage，provider 没报就估算 _estimate_response_usage）。这一层保证无论哪个 provider、哪种流式形态，runner 主循环看到的都是统一的 LLMResponse。

7上下文治理：三层防线context_governance.py

「一个 turn 里上下文会不会爆」由三层机制回答，前一层兜不住才轮到下一层：

第 1 层 · 单结果

每个工具结果 append 前（runner.py:537）：maybe_persist_tool_result 把超过 max_tool_result_chars 的输出 offload 到工作区文件，消息里只留文件路径引用；无 workspace 则硬截断。TOOL_RESULT_OFFLOAD_EXEMPT_TOOLS 豁免。

第 2 层 · 每请求

每次调 LLM 前（_request_model 第一步，context_governance.py:593）：估算 tokens vs input_budget（窗口 − max_output − buffer）。超预算：有 ContextCompactionState → _compact_request_history（:521）用 LLM 把已接受历史摘要成 checkpoint，保留增量；否则 → fit_to_budget（:336）尾部保留 + 清孤儿 tool result。仍不行抛 ContextWindowExceededError。

摘要会滚动累积

active_summary

下次再撞预算时，consolidate_history(待压缩历史, 旧摘要) —— 新摘要是把增量合并进旧摘要，不是从 60 条重摘一遍。摘要是滚动的、越压越稳定。

只压「已接受」部分

每次请求成功后 compaction.accept_request 推进边界。本 turn 迭代中刚 append 的消息属于 delta，永远原样保留，压缩只动确认过的历史。

两层是配合的

offload × compaction

第 1 层保证单个工具结果进历史前就是「轻」的（500KB → 文件引用）；第 2 层面对的 62 条历史因此都是可摘要的文本。没有第 1 层，摘要调用自己就会先爆。

turn 结束后生效

容易踩坑的细节

  • 会话内串行：同一 session 的两条消息永远不会并发跑 turn（_get_session_lock），但不同会话完全并发。
  • ephemeral turn：不写 session 历史、不存 checkpoint、usage 不落 _last_usage —— 摘要生成、Dream 等内部任务用它，避免污染用户会话。
  • provider 压缩后作废 provider_state：provider_compaction_applied 时（loop.py:2043-2050）必须清掉 opaque continuation，下次从 portable summary checkpoint 重建，否则会请求一个已被服务端重写过的会话。
  • 错误也要留占位：_append_model_error_placeholder 防止悬空 tool_calls 卡死会话（见上文卡片）。
  • suppress_response：turn 中工具已经自己给用户发过消息（capture_message_deliveries 探测），最终回复就不再重复发送。
  • SYSTEM turn 的回信：靠 restore 阶段 _remember_session_route 记住的路由找到回信地址，响应走 background_response。
  • usage 归因：bind_llm_usage_source 在 runner 生命周期内绑定 source，round_usages 逐轮记录后 merge 成总 usage，provider 不报时用 _estimate_response_usage 估算。
